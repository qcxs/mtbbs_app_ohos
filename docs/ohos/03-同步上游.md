# 同步上游（mtbbs）更新

> 适用：主线 `mtbbs` 发布新提交/版本后，把更新合并进本鸿蒙仓库。
>
> 本仓库是**独立项目**：只在鸿蒙上构建，`lib/` 与上游保持一致，鸿蒙特有内容只有
> `ohos/`、`pubspec_overrides.yaml`、`docs/ohos/`。

## 0. 项目生命周期

| 阶段 | 做什么 | 产物/记录 |
|---|---|---|
| 上游开发 | 主线 `mtbbs` 正常提交、打 tag | 上游 commit / tag |
| 鸿蒙基线 | 首次把鸿蒙改动提交；之后每次同步后提交 | 本仓库 commit |
| 同步触发 | 上游发版、重要修复、依赖升级后 | 合并提交 |
| 同步执行 | 按第 2 节合并 + 第 7 节验证 | 验证日志 |
| 发布 | 签名 → HAP → 真机冒烟 → 打 tag | `entry-default-signed.hap`、`ohos-vX.Y.Z` |
| 修复策略 | 通用问题修上游；鸿蒙专属问题只动 `ohos/` 或 `lib/platform/ohos/` | 上游 PR / 本仓库提交 |

**首次启用同步前必须有一次干净的基线提交**（当前工作区还未提交）。否则 `git merge`
会把“未提交的鸿蒙改动”和“上游改动”混在一起，无法回滚。

AI 执行同步时使用 [04-AI同步提示词.md](./04-AI同步提示词.md)，不要临场自由发挥。

## 1. 远程配置

推荐两个 remote：

| remote | 指向 | 用途 |
|---|---|---|
| `upstream` | `https://github.com/qcxs/mtbbs_app.git` | 拉取主线更新 |
| `origin` | 你自己的鸿蒙仓库地址 | 推送本仓库 |

```powershell
git remote -v
# 首次配置：
git remote add upstream https://github.com/qcxs/mtbbs_app.git
git remote add origin <你的鸿蒙仓库地址>
```

## 2. 合并流程

```powershell
# 1) 拉取上游（含 tag）
git fetch upstream --tags

# 2) 合并到当前分支（通常是 main）
git merge upstream/main

# 3) 只在下面三类文件解决冲突：
#    pubspec_overrides.yaml / docs/ohos/ / ohos/（很少同时改到）

# 4) 用 Flutter-OH SDK 重新解析并验证（项目已用 fvm 固定版本）
fvm flutter pub get
fvm flutter analyze lib
fvm flutter run -d <device-id>
```

出包前再跑一次第 7 节的 `build hap`。首次 clone 后如果 `.fvmrc` 未生效，先执行：

```powershell
fvm use flutter_ohos/oh-3.44.9-dev --skip-pub-get
```

## 3. 冲突纪律（保证下次还能干净合并）

1. **不改 `lib/` 业务文件**：跨平台差异由主线的 `AppCapabilities` 处理
   （见主线 `docs/23-可选能力与平台降级.md`）。
2. **不改 `pubspec.yaml`**：所有依赖差异放 `pubspec_overrides.yaml`。
3. `ohos/`、`pubspec_overrides.yaml`、`docs/ohos/` 是鸿蒙仓库专属，上游不会碰。
4. 确实需要鸿蒙专属代码时，只新增 `lib/platform/ohos/` 下的文件；能做成通用钩子的，
   优先提到主线（例如新增一个 `AppCapability`），这样两边都受益。

## 4. 上游升级依赖时

主线 `pubspec.yaml` 升级了被覆盖的 4 个插件后，先检查 OH fork 是否有对应分支：

| 插件 | 当前 OH ref |
|---|---|
| `path_provider` | `br_path_provider-v2.1.5_ohos` |
| `url_launcher` | `br_url_launcher-v6.3.2_ohos` |
| `flutter_inappwebview` | `br_v6.1.5_ohos` |
| `file_picker` | `br_v8.0.7_ohos` |

- 有对应分支：更新 `pubspec_overrides.yaml` 的 `ref`，再 `pub get` + `analyze`。
- 没有对应分支：优先保持旧 fork（API 兼容时通常可继续用），并在本文件记录差异；
  若 API 已不兼容，再评估是否临时关闭对应能力。

## 5. 上游新增可选插件时

主线新增依赖插件后：

1. 先看它是否有 OH 实现；
2. 有：无需处理；
3. 没有：在主线 `AppCapabilities` 中把对应能力在鸿蒙上设为 `false`，并让入口降级；
   然后本仓库 merge 主线即可（不要在本仓库改业务代码）。

## 6. 回滚

合并出问题时：

```powershell
git merge --abort          # 合并尚未完成
# 或已提交后：
git reset --hard HEAD~1    # 仅本地，确认没有未推送提交时使用
```

> 不要把 `pubspec_overrides.yaml` 从仓库删除来“恢复主线”：本仓库不构建 Android/Windows，
> 删掉它只会让鸿蒙构建失败。

## 7. 发布与版本

同步并验证通过后：

```powershell
# 真机 release（已在 DevEco 配好签名时去掉 --no-codesign）
fvm flutter build hap --release --target-platform ohos-arm64

# 打鸿蒙侧 tag，tag message 记录本次同步到的上游提交
git tag -a ohos-v1.0.9 -m "sync upstream $(git rev-parse --short upstream/main)"
git push origin main --tags
```

- 产物：`build\ohos\hap\entry-default-signed.hap`
- 版本号可沿用 `scripts/version.ps1`（与平台无关）
- 发布前至少冒烟：首页 → 帖子详情 → 图片 → 登录 → 发帖/回复 → 人机验证
- 每次发布在 tag message 里写明上游 commit，方便下次定位差异

## 8. AI 同步入口

把 [04-AI同步提示词.md](./04-AI同步提示词.md) 的提示词整段交给 AI，并告诉它：

```text
仓库：C:\files\project\flutter\mtbbs_app_ohos
任务：同步 upstream/main 并验证鸿蒙构建
```

AI 会先检查工作区是否干净；不干净会停下来让你处理，不会擅自合并。
