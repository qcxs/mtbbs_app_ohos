# 同步上游（mtbbs）更新

> 适用：主线 `mtbbs` 有新提交后，把更新合并进本鸿蒙仓库；也适用于**给鸿蒙仓库加特有功能**
> 时判断"该改哪个仓库"。本文是 AI 执行同步的**唯一操作手册**，04 号提示词会要求 AI 严格照此执行。
>
> 前置：本仓库是**独立项目**，只面向 Flutter-OH 构建。它自带依赖配置、自带原生工程，
> 与主线共享的只有 `lib/`、`assets/`、`test/`、`tool/`、`docs/` 这些 Dart/文档资产。

## 0. 一页结论（先读这段）

| 问题 | 答案 |
|---|---|
| `lib/` 能不能改？ | 只有 **`lib/ohos/**`** 可以（下游专属目录）。`lib/` 其余文件一律取上游，同步后 `robocopy /L` 预览必须无输出 |
| 鸿蒙特有功能放哪？ | 原生能力（通道、权限、通知、窗口、插件）→ 只写 `ohos/`；需要 Dart → **`lib/ohos/`**；需要**随 App 自动注册的 Dart 插件** → `packages/` 下的独立包；说明文档 → `docs/ohos/` |
| 鸿蒙特有 Dart 代码为什么不写进上游文件？ | 上游文件一旦有下游改动，文件级同步会把它覆盖掉，上游大重构时也无从判断哪些该保留；`lib/ohos/` 上游永不存在，**零覆盖**，重构后若 import 失效由 `flutter analyze` 立刻报错，改下游自己的文件即可 |
| 上游改动与下游定制的文件能不能"保留两边"？ | 只有 4 个混合文件（`pubspec.yaml`、`AGENTS.md`、`README.md`、`.gitignore`/`.metadata`）逐项手工合并；其余按矩阵整文件镜像，混改必然导致下次同步更难 |
| 上游把已删除的平台目录又带回来了？ | 镜像只同步 `lib/ assets/ test/ tool/ docs/`，平台目录天然不会被带入；若上游新增了平台目录，按第 5 节兜底删除 |
| 依赖版本差异写哪？ | `pubspec.yaml` 末尾的 `dependency_overrides` **整段**（本仓库自有），上游的 `dependencies` 原样接受 |
| 怎么同步？ | **文件级镜像**（`robocopy /MIR` + 排除清单），**不用 `git merge`**；git 只用来查看上游改了什么、确认下游干净（见第 3 节） |
| 上游有未提交改动，能同步吗？ | **能**。上游**工作区当前内容**就是同步源（含未提交文件）；记录来源 HEAD 供追溯即可 |
| 和鸿蒙无关的新功能该在哪做？ | **先在上游做**。下游只做平台适配，不新增通用特性（外部参考 PiliPlus-ohos 的公开纪律：分支只适配鸿蒙、不新增特性，见第 13 节） |

**判断口诀**：Dart 侧（`lib/`）无鸿蒙专属代码（鸿蒙 Dart 只在 `lib/ohos/` 与 `packages/`）；
鸿蒙差异 = 原生工程 + 依赖覆盖 + 平台能力开关；同步 = 上游文件整体镜像 + 4 个固定混合文件手工合并。

## 1. 文件归属矩阵（同步时逐类照做）

| 路径 | 归属 | 同步动作 |
|---|---|---|
| `lib/**`（**不含 `lib/ohos/`**） | 上游 | **镜像覆盖**（`robocopy /MIR`）：上游新增自动带入、上游删除自动删除。若镜像前 `git status` 显示这些文件有下游差异 → **停下**，把差异迁到 `lib/ohos/` 再说 |
| `lib/ohos/**` | **下游** | 排除镜像（`/XD`），全部保留下游；新增鸿蒙 Dart 逻辑只放这里，含自定义入口 |
| `packages/**` | **下游** | 上游不存在该目录，镜像清单（lib/assets/test/tool/docs）天然不碰；**不要搬运到上游**。目前只有 `mtbbs_ohos_bridge`（接续 Dart 插件，见 `docs/ohos/05` §5.1） |
| `assets/`、`test/`、`tool/` | 上游 | 镜像覆盖 |
| `docs/**`（除 `docs/ohos/`） | 上游 | 镜像覆盖；但下游**有意删除**的 `docs/15-版本发布.md` 用 `/XF` 排除（见第 5 节） |
| `pubspec.yaml` 的 `dependencies` / `dev_dependencies` / `flutter:` | 上游 | 手工合并：以上游文件为底（第 4.3 节） |
| `pubspec.yaml` 的 `dependency_overrides`（末尾带长注释的那段） | **下游** | **整段保留下游**；上游若新增同名 key，先按上游版本号确认 fork 是否可用，再保留下游的 git 源 |
| `pubspec.lock` | 生成物 | 不镜像；同步后跑 `fvm flutter pub get` 重新生成（overrides 会写成 fork 的版本） |
| `ohos/**` | **下游** | 全部保留下游；上游不会新增该目录，镜像带入说明上游误加，停下来问 |
| `docs/ohos/**` | **下游** | 全部保留下游 |
| `.fvmrc`、`.fvm/` | 下游 | 保留下游（鸿蒙固定 Flutter-OH SDK；`.fvm/` 不入库） |
| `.local/**` | 下游、**未跟踪** | 不提交、不合并 |
| `android/`、`windows/`、`installer/`、`.github/`、`ios/`、`macos/`、`linux/` | **已删除** | 镜像本来就不含它们；上游若新增，按第 5 节兜底删除 |
| `scripts/`（`version.ps1` 等） | 上游为主 | 镜像后若上游改动，补回下游的鸿蒙段落，登记到第 9 节 |
| `AGENTS.md`、`README.md`、`.gitignore`、`.metadata` | 混合 | 手工合并，见 4.2 |
| 其他任何文件 | 未知 | **停下并汇报**，不要猜 |

## 2. 开工前的停止条件（任一命中就停，不要自作主张）

1. **下游** `git status --short` 有任何输出（含未跟踪文件）——先让人提交，镜像前的干净基线是事后
   定位"本次同步改了什么"的唯一依据，不要 stash/reset。
2. 当前分支不是 `main`（或人明确指定的分支）。
3. 发现 `lib/`（**排除 `lib/ohos/`**）里有**上游不存在的下游改动**（把上游内容与下游逐个文件比对后
   仍多出差异）——说明有人手改了上游文件，先迁到 `lib/ohos/`。
4. 需要改动 `lib/` 的**上游文件**才能让构建/分析通过——先停，说明"该能力要么写 `lib/ohos/`，要么上游化"。
5. 镜像目标目录不可写 / robocopy 报 `Access denied`——先停，检查是否被编辑器或杀毒占用。

> 上游**不要求**工作区干净：上游当前内容（含未提交改动）就是同步源。只需在汇报里记录来源 HEAD 与
> 未提交文件数量，便于追溯。

## 3. 同步流程（文件级镜像，常态方式）

### 3.1 为什么不用 `git merge`

下游历史上用 **squash 同步**，上游提交 hash 不在下游历史里，`git merge` 的 merge base 会失真，
结果是"每个上游文件都冲突"；上游根目录还多出 `android/windows/installer/ios/macos/linux`、
下游少了 `docs/15`，每轮都要手工删除复活目录。改用**文件级镜像**后：

- 合并规则退化成"上游文件整体覆盖 + 排除下游专属目录 + 4 个固定混合文件手工合并"；
- 上游新增/删除文件自动带入，不会再有"改哪个文件"的判断；
- 代价是**丢失 git 合并记录**：所以每轮必须登记同步来源（第 9 节表末），git 只作参考。

git 在新流程里的三个用途：看上游改了什么（`log/diff/show`）、确认下游干净（`status`）、
对比文件内容（`diff --no-index`）。

### 3.2 执行

```powershell
$UP = "C:\files\project\flutter\mtbbs"          # 上游主线工作区（本地优先）
$DS = "C:\files\project\flutter\mtbbs_app_ohos" # 本仓库

# 0) 自检（见第 2 节）
git -C $DS status --short
git -C $DS branch --show-current

# 1) 只读取上游改了什么（供汇报/理解，不参与合并）
git -C $UP log --oneline -10
git -C $UP status --short          # 未提交内容同样算"最新代码"
git -C $UP diff --stat HEAD~3..HEAD

# 2) 集合侦察：确认不会误删下游专属文件（下面两条都应为空输出）
Compare-Object `
  (Get-ChildItem $UP\lib -Recurse -File | ForEach-Object { $_.FullName.Substring("$UP\lib".Length) } | Where-Object { $_ -notlike '*\ohos\*' }) `
  (Get-ChildItem $DS\lib -Recurse -File | ForEach-Object { $_.FullName.Substring("$DS\lib".Length) } | Where-Object { $_ -notlike '*\ohos\*' })
Compare-Object `
  (Get-ChildItem $UP\docs -Recurse -File | ForEach-Object { $_.FullName.Substring("$UP\docs".Length) } | Where-Object { $_ -notlike '*\ohos\*' -and $_ -notlike '*15*' }) `
  (Get-ChildItem $DS\docs -Recurse -File | ForEach-Object { $_.FullName.Substring("$DS\docs".Length) } | Where-Object { $_ -notlike '*\ohos\*' })

# 3) 镜像（/MIR = 覆盖 + 删除上游已不存在的文件）
robocopy $UP\lib    $DS\lib    /MIR /XD $DS\lib\ohos
robocopy $UP\assets $DS\assets /MIR
robocopy $UP\test   $DS\test   /MIR
robocopy $UP\tool   $DS\tool   /MIR
robocopy $UP\docs   $DS\docs   /MIR /XD $DS\docs\ohos /XF "15-版本发布.md"

# 4) 4 个混合文件手工合并（第 4.2、4.3 节）：pubspec.yaml / AGENTS.md / README.md / .gitignore
# 5) 兜底清理（镜像已排除，这里只防止上游把平台目录"带回来"）
git -C $DS rm -r --ignore-unmatch android windows installer .github ios macos linux
```

> robocopy 退出码：`0` 无变化、`1` 有复制、`3` 有复制+删除、`>=8` 失败。前三种都算成功。
> 中文文件名（`docs/15-版本发布.md`）按原样传入 `/XF` 即可。

首次 clone 若 `.fvmrc` 未生效：

```powershell
fvm use flutter_ohos/oh-3.44.9-dev --skip-pub-get
```

## 4. 差异处理细则（文件级同步没有 merge 冲突，只有三类差异）

### 4.1 `lib/`：多出 / 缺失 / 内容不一致

镜像后正常情况下 `lib/` 应与上游完全一致（`lib/ohos/` 除外）。异常只有两种：

| 现象 | 含义 | 处理 |
|---|---|---|
| 镜像后仍有下游文件是上游没有的 | 有人在上游文件里加了下游逻辑 | 迁到 `lib/ohos/`，再重跑镜像 |
| 镜像后上游文件仍显示"内容不同" | 文件被占用，robocopy 未覆盖 | 看退出码；原样重跑一次，仍失败先停 |

不要为了保住下游改动而手工混合两个版本。

### 4.2 混合文件（`AGENTS.md` / `README.md` / `.gitignore` / `.metadata`）

以**上游文件为底**，补回下列下游内容；每次同步逐项核对，缺一项就是回归：

- **`AGENTS.md`**
  - 保留"相关项目／鸿蒙仓库专属"段落与 `docs/ohos/` 路由行（构建、同步上游、应用流转等）
  - 上游**铁律与路由表的新增行必须全量吸收**（2026-10-30 一轮新增：铁律 5 的
    `threads.sembast` 例外、路由 `26`、路由 `24 + 25`）
  - 删除 `docs/15` 路由行（本仓库无该文档）
- **`README.md`**
  - 保留鸿蒙构建章节（默认 `lib/main.dart`，接续由 Dart 插件自动注册）与 `docs/ohos` 子树
  - 上游**功能表与文档树的新增行必须全量吸收**（2026-10-30 一轮新增：帖子缓存功能行、
    文档树 24/25/26）
  - 平台描述保留下游措辞（如生成图片"存相册，不可用时回退另存为"）
- **`.gitignore`**：保留下游版本（已删 Android/Windows 规则）；上游新增**非平台**条目时要吸收
- **`.metadata`**：保留下游版本（OH SDK 会把它改成 fork 的 revision，提交前还原）

### 4.3 `pubspec.yaml`

1. 以上游文件为底（`dependencies` / `dev_dependencies` / `flutter:` 原样接受，含注释）。
2. 末尾追加本仓库的 `dependency_overrides` 段（从上次提交的 `pubspec.yaml` 整段复制，含长注释）。
3. 只有上游把被覆盖插件升到新版本时，才按第 6 节更新 `ref`。
4. 完成后校验：`git diff --no-index <上游>/pubspec.yaml pubspec.yaml` 只应显示
   `dependency_overrides` 段与上游注释的同步。

## 5. 清理兜底（排除清单就是清理规则）

本仓库刻意只保留鸿蒙平台。文件级镜像只同步 `lib/ assets/ test/ tool/ docs/`，平台目录天然不会被带入；
`docs/15` 已在镜像命令里用 `/XF` 排除。剩余只需兜底检查：

```powershell
# 上游若新增平台目录、或有人手动带入，按此删除
git -C $DS rm -r --ignore-unmatch android windows installer .github ios macos linux docs/15-版本发布.md
git -C $DS status --short        # 确认只出现预期内的改动
```

> 这些删除属于"本仓库的既定状态"，不是丢失上游内容：上游仍然完整保存它们。
> 不要为了"同步完整"而恢复这些目录。

## 6. 依赖覆盖维护

`pubspec.yaml` 的 `dependency_overrides` 当前指向：

| 插件 | 上游版本 | OH fork ref |
|---|---|---|
| `path_provider` | 2.1.6 | `br_path_provider-v2.1.5_ohos` |
| `url_launcher` | 6.3.2 | `br_url_launcher-v6.3.2_ohos` |
| `flutter_inappwebview` | 6.1.5 | `br_v6.1.5_ohos` |
| `file_picker` | 8.3.7 | `br_v8.0.7_ohos`（OH 侧无 8.3.7） |
| `web`（传递依赖） | 1.1.x | 钉 `^1.1.0`，解 `file_picker` 与 `inappwebview_web` 的约束冲突 |

上游升级这些插件后：

1. 先查 OH fork 是否有对应分支；
2. 有 → 只改 `dependency_overrides` 里的 `ref`；
3. 没有 → 保持旧 fork（API 兼容时通常可用），并把差异写进 `docs/ohos/01-环境与构建.md` 的依赖表；
4. 绝不为了对齐上游而移除覆盖项——那会让鸿蒙构建直接失败。

**每条覆盖都要写清"fork 仓库 + 分支 + 用途 + 是否已提交上游"**（参考 PiliPlus-ohos 的
`docs/HDR.md` 依赖表：`media_kit` / `mpv` / `FFmpeg` 各自的 fork 分支 `feat-ohos-hdr`，
并注明"后续计划提交给上游"）。没提交上游的要登记原因，便于上游插件升级时复核。

上游**新增**可选插件（`lib/platform/optional/` 里的适配器）：先看有没有 OH 实现；
没有就让上游在 `AppCapabilities` 里对该平台关闭能力（见上游 `docs/23`），本仓库只合并，不改业务代码。

## 10. 回滚

镜像前已确认下游干净，所以回滚 = 回到最后一次提交：

```powershell
git -C $DS checkout -- .                          # 丢弃镜像覆盖与手工合并
git -C $DS clean -fd lib assets test tool docs    # 删除镜像新增的未跟踪文件（不要加 -x）
git -C $DS status --short                          # 必须为空
```

已提交但验证失败：用 `git revert <提交>`，不要 `git reset --hard`（会连带丢掉后续工作）。

不要用"删掉 `dependency_overrides`"来假装回到主线——本仓库不构建 Android/Windows，
删掉只会让鸿蒙构建失败。

## 13. 外部参考：PiliPlus-ohos 是怎么同步上流的

同为本机上的 Flutter 鸿蒙版（`C:\files\project\flutter\PiliPlus-ohos`），它的做法与我们的差异：

| 维度 | PiliPlus-ohos | 本仓库 | 结论 |
|---|---|---|---|
| 与上游的关系 | 同仓同包的**长期分支**，靠人工 merge | 独立仓库 + AI 照手册 merge | 我们更依赖手册，所以归属矩阵必须写死（已有） |
| 同步原则 | README 明写"分支只把 PiliPlus 适配到鸿蒙；几乎所有与鸿蒙无关的功能都是上游实现的""分支需要同步上游，一般不增加新功能或改变特性" | 第 0 节已加入同一条原则 | **值得照抄的纪律**：通用功能先上游，下游只做适配 |
| Dart 侧专属代码 | 集中在 `lib/harmony_adapt/`，但页面/控制器里有少量侵入调用（如 `HarmonyChannel.holdContinuation(this)`） | 只允许 `lib/ohos/`，上游文件 0 改动 | 它因为可以随便改 `lib/` 才这么写；我们**不能**照抄侵入点，需换成"路由监听"式零侵入（见 05 §4.4） |
| 依赖改造 | 直接改 `dependencies` 指向各 fork/gitcode 的 `*_ohos` 包与分支（`feat-ohos-hdr` 等），并在 `docs/HDR.md` 列"仓库 / 内容 / 计划提交上游" | 上游 `dependencies` 不动，差异全在 `dependency_overrides` | 我们的方式合并更省事；**它记录 fork 用途与"计划上游化"的做法值得补进第 6 节** |
| 同步自动化 | `.github/workflows` 只有 `pr_check`、`release`，**没有**上游同步流水线 | 有 03 手册 + 04 提示词 + 验证清单 | 它靠人工记忆，我们比它更完备，不必回退 |
| 平台差异文档 | `docs/` 下按**专题**单篇写（如 `HDR.md`：为什么纹理做不到 / 方案 / 依赖 / 设置 / 信令） | `docs/ohos/` 按流程分篇 | 值得借鉴的形态：**单个鸿蒙特有能力写一篇"决策 + 坑 + 验证"专题**，比塞进流程文档更易查 |

可直接落实的三条（已落点）：

1. **功能分流纪律**：与鸿蒙无关的新功能先在上游做（第 0 节）。
2. **依赖覆盖登记**：fork 仓库 + 分支 + 用途 + 是否已提交上游（第 6 节）。
3. **专题文档**：新鸿蒙特有能力除写代码外，另写一篇 `docs/ohos/` 专题（示例即本仓库的 05 号）。

## 14. 同步方式选型与可选优化

### 14.1 三种方式对比（结论：文件级镜像）

| 方式 | 适用 | 在本仓库的问题 |
|---|---|---|
| `git merge local-upstream/main` | 上下游共享线性历史 | 下游历史上是 squash 同步，merge base 失真 → 几乎每个 `lib/` 文件都冲突；平台目录与 `docs/15` 反复复活 |
| `git cherry-pick` 逐提交 | 上游提交少且干净 | 上游一次重构涉及几十个文件，逐提交挑等于手工重演；上游未提交内容也不在提交里 |
| **文件级镜像（本仓库采用）** | 下游只保留上游的 Dart/文档资产 + 自有平台工程 | 上游新增/删除自动带入，规则只剩"排除专属目录 + 手工合并 4 个文件"；代价是丢失 git 合并记录（用 9.1 表补偿） |

本轮实测（2026-10-30）：镜像 + 4 个手工文件，从上游 `bc9a9e7` 同步完成，
`pub get`、`analyze lib`、`build hap` 全通过，无逐文件冲突。

### 14.2 可选优化（按收益排序，均未强制落地）

1. **`pubspec_overrides.yaml`**：Flutter 原生支持把 `dependency_overrides` 放到独立文件，
   这样 `pubspec.yaml` 可以 **100% 镜像上游**，手工合并文件从 4 个降到 3 个。
   落地前必须验证：`fvm flutter pub get` 后 `.flutter-plugins-dependencies` 的 ohos 段
   仍解析到 fork 版本；不生效就回退（把整段搬回 `pubspec.yaml`，无其他影响）。
2. **一键脚本 `scripts/sync-upstream.ps1`**：把第 3.2 节镜像与第 7 节 `/L` 校验固化为一条命令，
   参数化 `$UP` / `$DS`，输出改动清单与校验结果，避免每次手抄。属下游脚本，需在第 9 节登记。
3. **同步记录自动化**：由脚本追加 9.1 表新行，或生成 `docs/ohos/sync-log.md`（条目式），
   避免 03 越写越长。

不建议 `git subtree` / `git submodule`：上游是完整主项目、下游是独立 fork；
subtree 会把上游平台目录一并纳入（再删一次又污染提交），submodule 则无法承载下游自有 `ohos/`。
