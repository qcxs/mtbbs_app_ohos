# 同步上游（mtbbs）更新

> 适用：主线 `mtbbs` 有新提交后，把更新合并进本鸿蒙仓库；也适用于**给鸿蒙仓库加特有功能**
> 时判断"该改哪个仓库"。本文是 AI 执行同步的**唯一操作手册**，04 号提示词会要求 AI 严格照此执行。
>
> 前置：本仓库是**独立项目**，只面向 Flutter-OH 构建。它自带依赖配置、自带原生工程，
> 与主线共享的只有 `lib/`、`assets/`、`test/`、`tool/`、`docs/` 这些 Dart/文档资产。

## 0. 一页结论（先读这段）

| 问题 | 答案 |
|---|---|
| `lib/` 能不能改？ | 只有 **`lib/ohos/**`** 可以（下游专属目录）。`lib/` 其余文件一律取上游，合并后 `git diff <upstream>/main -- lib ':!lib/ohos'` 必须为空 |
| 鸿蒙特有功能放哪？ | 原生能力（通道、权限、通知、窗口、插件）→ 只写 `ohos/`；需要 Dart → **`lib/ohos/`**；说明文档 → `docs/ohos/` |
| 鸿蒙特有 Dart 代码为什么不写进上游文件？ | 上游文件一旦有下游改动，上游大重构（拆文件/改名）就会制造 merge 冲突；`lib/ohos/` 上游永不存在，**零冲突**，重构后若 import 失效由 `flutter analyze` 立刻报错，改下游自己的文件即可 |
| 冲突了能不能"保留两边"？ | 不能。矩阵里写"上游"就整文件取上游，写"下游"就整文件取下下游；混改必然导致下次合并更难 |
| 上游把已删除的平台目录又带回来了？ | 合并完成后**立刻重新删除**（第 5 节），这是本项目刻意保持"只有鸿蒙"的代价 |
| 依赖版本差异写哪？ | `pubspec.yaml` 末尾的 `dependency_overrides` **整段**（本仓库自有），上游的 `dependencies` 原样接受 |
| 和鸿蒙无关的新功能该在哪做？ | **先在上游做**。下游只做平台适配，不新增通用特性（外部参考 PiliPlus-ohos 的公开纪律：分支只适配鸿蒙、不新增特性，见第 13 节） |

**判断口诀**：Dart 侧（`lib/`）无鸿蒙专属代码；鸿蒙差异 = 原生工程 + 依赖覆盖 + 平台能力开关。

## 1. 文件归属矩阵（AI 遇到冲突就查这张表）

| 路径 | 归属 | 合并时怎么做 |
|---|---|---|
| `lib/**`（**不含 `lib/ohos/`**） | 上游 | 整文件取上游。若合并前 `git status` 显示这些文件有下游差异 → **停下**，把差异迁到 `lib/ohos/` 再说 |
| `lib/ohos/**` | **下游** | 全部保留下游（上游永不存在该目录）；新增鸿蒙 Dart 逻辑只放这里，含自定义入口 |
| `assets/`、`test/`、`tool/` | 上游 | 取上游 |
| `docs/**`（除 `docs/ohos/`） | 上游 | 取上游；但下游**有意删除**的 `docs/15-版本发布.md` 保持删除（见第 5 节） |
| `pubspec.yaml` 的 `dependencies` / `dev_dependencies` / `flutter:` | 上游 | 取上游 |
| `pubspec.yaml` 的 `dependency_overrides`（末尾带长注释的那段） | **下游** | **整段保留下游**；上游若新增同名 key，先按上游版本号确认 fork 是否可用，再保留下游的 git 源 |
| `pubspec.lock` | 生成物 | 冲突时先取任一版本，再跑 `fvm flutter pub get` 重新生成（overrides 会写成 fork 的版本） |
| `ohos/**` | **下游** | 全部保留下游；上游不会新增该目录，出现冲突说明上游误加，停下来问 |
| `docs/ohos/**` | **下游** | 全部保留下游 |
| `.fvmrc`、`.fvm/` | 下游 | 保留下游（鸿蒙固定 Flutter-OH SDK；`.fvm/` 不入库） |
| `.local/**` | 下游、**未跟踪** | 不提交、不合并 |
| `android/`、`windows/`、`installer/`、`.github/`、`ios/`、`macos/`、`linux/` | **已删除** | 合并后重新删除（第 5 节） |
| `scripts/`（`version.ps1` 等） | 上游为主 | 冲突优先上游，再补回下游的鸿蒙段落；改完登记到第 9 节 |
| `AGENTS.md`、`README.md`、`.gitignore`、`.metadata` | 混合 | 见 4.2 |
| 其他任何文件 | 未知 | **停下并汇报**，不要猜 |

## 2. 开工前的停止条件（任一命中就停，不要自作主张）

1. `git status --short` 有任何输出（含未跟踪文件）——先让人处理干净，不要 stash/reset/merge。
2. 从**本地主线**同步时，上游目录 `git -C <上游> status --short` 有输出——未提交内容无法被 fetch，
   让人先在上游提交。
3. 当前分支不是 `main`（或人明确指定的分支）。
4. 发现 `lib/`（**排除 `lib/ohos/`**）里有上游不存在的下游改动（合并前
   `git diff <upstream>/main -- lib ':!lib/ohos'` 就非空）。
5. 需要改动 `lib/` 的**上游文件**才能让构建/分析通过——先停，说明"该能力要么写 `lib/ohos/`，要么上游化"。

## 3. 合并流程

远程约定：`local-upstream` = 本机主线目录（优先），`upstream` = GitHub `qcxs/mtbbs_app`（兜底），
`origin` = 本鸿蒙仓库。

```powershell
# 0) 自检（见第 2 节）
git status --short
git branch --show-current

# 1) 拉取：本机主线优先
git fetch local-upstream --tags        # 本地主线不存在时才用: git fetch upstream --tags

# 2) 先看要合并什么
git log --oneline HEAD..local-upstream/main
git diff --stat HEAD...local-upstream/main

# 3) 合并（不要用 rebase，保留真实合并历史，方便下次定位）
git merge local-upstream/main

# 4) 冲突按第 1 节矩阵处理；只允许对矩阵里明确标注的文件 `git checkout --theirs/--ours`
# 5) 合并收尾后立刻执行第 5 节清理，再执行第 6、7 节
```

首次 clone 若 `.fvmrc` 未生效：

```powershell
fvm use flutter_ohos/oh-3.44.9-dev --skip-pub-get
```

## 4. 冲突处理细则

### 4.1 `lib/` 冲突

正常情况下**不该出现**（`lib/ohos/` 除外）：出现了说明有人把鸿蒙逻辑散写进了上游文件，
应先迁到 `lib/ohos/`。临时处理顺序：

1. 取上游：`git checkout --theirs -- <file>` + `git add <file>`；
2. 在汇报里逐个列出被覆盖的下游改动，并说明"该功能需先上游化"；
3. 不要为了保住下游改动而手工混合两个版本。

### 4.2 混合文件（`AGENTS.md` / `README.md` / `.gitignore` / `.metadata`）

- **`.metadata`**：取上游版本（OH SDK 会把它改成 fork 的 revision，提交前还原）。
- **`.gitignore`**：取上游，再补回本仓库的两条鸿蒙规则（`ohos/` 构建产物、`.local/`）。
- **`AGENTS.md` / `README.md`**：取上游，再保留"鸿蒙仓库专属"段落（构建命令、`docs/ohos/` 链接、
  `dependency_overrides` 说明）。合并后用 `git diff` 人工确认这两段仍在。

### 4.3 依赖冲突（`pubspec.yaml`）

1. `dependencies` / `dev_dependencies` 一律取上游（含注释）。
2. `dependency_overrides` 整段取下下游；只有上游把被覆盖插件升到新版本时，才按第 6 节更新 `ref`。
3. 合并完成后 `pubspec.yaml` 应满足：上游段落 == 上游文件内容，仅末尾多出本仓库的 `dependency_overrides` 段。

## 5. 合并后清理（上游会把这些"删掉的东西"带回来）

本仓库刻意只保留鸿蒙平台。上游每次改动这些目录，merge 都可能把文件重新写回工作区或产生删除冲突。
合并完成后**立刻**执行：

```powershell
git rm -r --ignore-unmatch android windows installer .github docs/15-版本发布.md
git rm -r --ignore-unmatch ios macos linux   # 上游若将来新增这些平台目录
git status --short                            # 确认只剩预期的删除
```

> 这些删除属于"本仓库的既定状态"，不是丢失上游内容：上游仍然完整保存它们。
> 不要为了"合并干净"而恢复这些目录。

## 6. 依赖覆盖维护

`pubspec.yaml` 的 `dependency_overrides` 当前指向：

| 插件 | 上游版本 | OH fork ref |
|---|---|---|
| `path_provider` | 2.1.6 | `br_path_provider-v2.1.5_ohos` |
| `url_launcher` | 6.3.2 | `br_url_launcher-v6.3.2_ohos` |
| `flutter_inappwebview` | 6.1.5 | `br_v6.1.5_ohos` |
| `file_picker` | 8.3.7 | `br_v8.0.7_ohos`（OH 侧无 8.3.7） |
| `web`（传递依赖） | 1.1.x | 钉 `^1.1.0`，解 `file_picker` 与 `inappwebview_web` 的约束冲突 |

上游升级这些插件后：

1. 先查 OH fork 是否有对应分支；
2. 有 → 只改 `dependency_overrides` 里的 `ref`；
3. 没有 → 保持旧 fork（API 兼容时通常可用），并把差异写进 `docs/ohos/01-环境与构建.md` 的依赖表；
4. 绝不为了对齐上游而移除覆盖项——那会让鸿蒙构建直接失败。

**每条覆盖都要写清"fork 仓库 + 分支 + 用途 + 是否已提交上游"**（参考 PiliPlus-ohos 的
`docs/HDR.md` 依赖表：`media_kit` / `mpv` / `FFmpeg` 各自的 fork 分支 `feat-ohos-hdr`，
并注明"后续计划提交给上游"）。没提交上游的要登记原因，便于上游插件升级时复核。

上游**新增**可选插件（`lib/platform/optional/` 里的适配器）：先看有没有 OH 实现；
没有就让上游在 `AppCapabilities` 里对该平台关闭能力（见上游 `docs/23`），本仓库只合并，不改业务代码。

## 9. 下游差异登记表（合并时对照；"应为空"的项非空就是问题）

| 项 | 预期 | 现状 |
|---|---|---|
| `lib/` 与上游差异（`lib/ohos/` 除外） | **必须为空** | 空 |
| `lib/ohos/` | 下游专属目录，每次合并都保留 | 见下 |
| `pubspec.yaml` 差异 | 仅 `dependency_overrides` 段 | 符合 |
| 平台工程 | 只有 `ohos/`，无 android/windows/installer/ios/macos/linux | 符合 |
| `docs/` 差异 | 少 `15-版本发布.md`（鸿蒙不发 GitHub Release） | 符合 |
| `scripts/version.ps1` | 与上游一致；如需鸿蒙专属逻辑，优先上游化，未上游化前在此登记 | 见下 |
| `.metadata` | 与上游一致 | 符合 |

> 新增任何"下游独有"的 Dart/脚本改动，都先尝试上游化；确实上游化不了的，才添加到本表并写明原因。

## 10. 回滚

```powershell
git merge --abort           # 合并尚未完成
git reset --hard ORIG_HEAD  # 已合并但验证失败（仅本地；确认没有要保留的改动）
```

不要用"删掉 `dependency_overrides`"来假装回到主线——本仓库不构建 Android/Windows，
删掉只会让鸿蒙构建失败。

## 11. 发布

```powershell
fvm flutter build hap --release --target lib/ohos/entry.dart --target-platform ohos-arm64
git tag -a ohos-vX.Y.Z -m "sync upstream $(git rev-parse --short local-upstream/main)"
git push origin main --tags
```

- 产物：`build\ohos\hap\entry-default-signed.hap`
- tag message 记录本次同步到的上游提交，方便下次定位差异
- 真机冒烟通过后再推 tag

## 13. 外部参考：PiliPlus-ohos 是怎么同步上流的

同为本机上的 Flutter 鸿蒙版（`C:\files\project\flutter\PiliPlus-ohos`），它的做法与我们的差异：

| 维度 | PiliPlus-ohos | 本仓库 | 结论 |
|---|---|---|---|
| 与上游的关系 | 同仓同包的**长期分支**，靠人工 merge | 独立仓库 + AI 照手册 merge | 我们更依赖手册，所以归属矩阵必须写死（已有） |
| 同步原则 | README 明写"分支只把 PiliPlus 适配到鸿蒙；几乎所有与鸿蒙无关的功能都是上游实现的""分支需要同步上游，一般不增加新功能或改变特性" | 第 0 节已加入同一条原则 | **值得照抄的纪律**：通用功能先上游，下游只做适配 |
| Dart 侧专属代码 | 集中在 `lib/harmony_adapt/`，但页面/控制器里有少量侵入调用（如 `HarmonyChannel.holdContinuation(this)`） | 只允许 `lib/ohos/`，上游文件 0 改动 | 它因为可以随便改 `lib/` 才这么写；我们**不能**照抄侵入点，需换成"路由监听"式零侵入（见 05 §4.4） |
| 依赖改造 | 直接改 `dependencies` 指向各 fork/gitcode 的 `*_ohos` 包与分支（`feat-ohos-hdr` 等），并在 `docs/HDR.md` 列"仓库 / 内容 / 计划提交上游" | 上游 `dependencies` 不动，差异全在 `dependency_overrides` | 我们的方式合并更省事；**它记录 fork 用途与"计划上游化"的做法值得补进第 6 节** |
| 同步自动化 | `.github/workflows` 只有 `pr_check`、`release`，**没有**上游同步流水线 | 有 03 手册 + 04 提示词 + 验证清单 | 它靠人工记忆，我们比它更完备，不必回退 |
| 平台差异文档 | `docs/` 下按**专题**单篇写（如 `HDR.md`：为什么纹理做不到 / 方案 / 依赖 / 设置 / 信令） | `docs/ohos/` 按流程分篇 | 值得借鉴的形态：**单个鸿蒙特有能力写一篇"决策 + 坑 + 验证"专题**，比塞进流程文档更易查 |

可直接落实的三条（已落点）：

1. **功能分流纪律**：与鸿蒙无关的新功能先在上游做（第 0 节）。
2. **依赖覆盖登记**：fork 仓库 + 分支 + 用途 + 是否已提交上游（第 6 节）。
3. **专题文档**：新鸿蒙特有能力除写代码外，另写一篇 `docs/ohos/` 专题（示例即本仓库的 05 号）。
