# 鸿蒙（OpenHarmony）环境与构建

> 适用：构建/调试鸿蒙 HAP、排查鸿蒙侧依赖问题。
>
> **本仓库是 mtbbs 的鸿蒙独立版**：只面向 Flutter-OH，不保证 Android / Windows 构建。
> `lib/` 的上游文件与上游保持一致（校验 `git diff <upstream>/main -- lib ':!lib/ohos'` 必须为空），
> 鸿蒙特有内容放 `ohos/`、`lib/ohos/`、`docs/ohos/` 和 `pubspec.yaml` 末尾的
> `dependency_overrides` 段。依赖覆盖**常驻生效**，不需要"用时生成、用完删除"。
>
> 与上游同步见 [03-同步上游.md](./03-同步上游.md)；从零部署见
> [02-从零部署指南.md](./02-从零部署指南.md)。
>
> **换机器请注意**：文中出现的 `C:\Users\admin\...`、`C:\Program Files\Huawei\...` 等是本机实测路径，
> 换成你自己的路径即可。**从零部署**（别人克隆本仓库后怎么配环境、怎么打包）见
> [02-从零部署指南.md](./02-从零部署指南.md)。

### 1.2 Flutter-OH SDK

鸿蒙用的是 Flutter 的**分支 SDK**（不是插件），与官方 SDK 并存互不冲突：

```powershell
# 注册 fork 别名（只需一次）
fvm fork add flutter_ohos https://gitcode.com/CPF-Flutter/flutter_flutter.git

# 安装（首次约 2.8 GB + 引擎产物）
fvm install flutter_ohos/oh-3.44.9-dev
```

选用 `oh-3.44.9-dev`（= `3.44.9+ohos-0.0.1-canary1` / Dart **3.12.2**）的原因：
`pubspec.yaml` 的 `sdk: ^3.12.2` 要求 Dart ≥ 3.12.2，而稳定的 `oh-3.35.7`（Dart 3.9.2）**不满足**。

> 2026-09 实测该仓库只有 `oh-3.41.9-dev` / `oh-3.41.9-release` / `oh-3.44.9-dev` 三条分支。

### 1.4 签名

- **调试安装**：DevEco Studio 打开 `ohos/` 目录 → File → Project Structure → Signing Configs →
  勾选 *Automatically generate signature*（**需要登录华为开发者账号**）。
  配置写入 `ohos/build-profile.json5` 的 `signingConfigs`，证书落在 `~/.ohos/config/`。
- **侧载分发**：出**无签名**包（`--no-codesign`），由使用者自行签名，见第 3 节。
- 未配签名时 `build hap --debug` 会在 `assembleHap` 之后停在签名步骤
  （提示「请通过 DevEco Studio 打开 ohos 工程后配置调试签名」），此时 ArkTS 编译已通过；
  只想验证编译就加 `--no-codesign`。
- 校验签名是否配置正确：`signingConfigs` 非空 + profile 的 `bundle-name` 与**目标变体**的包名一致
  （正式 `…mtbbs.ohos` / beta `…ohos.beta` / debug `…ohos.debug`，见 3.4）+ profile 的 `device-ids`
  含目标设备 UDID（`hdc shell bm get --udid`）。

## 2. 依赖适配

pub.dev 上的插件没有 `ohos` 实现，必须换成 OpenHarmony 社区维护的 fork。
本仓库把覆盖直接写在 `pubspec.yaml` 末尾的 `dependency_overrides` 段（不再使用
`pubspec_overrides.yaml`），`flutter pub get` 会直接使用，不需要"用时复制、用完删除"。

| 插件 | 上游版本 | OH fork | 分支 | 差异 |
|---|---|---|---|---|
| `path_provider` | 2.1.6 | `openharmony-tpc/flutter_packages` | `br_path_provider-v2.1.5_ohos` | 降 1 个小版本 |
| `url_launcher` | 6.3.2 | `openharmony-tpc/flutter_packages` | `br_url_launcher-v6.3.2_ohos` | 无 |
| `flutter_inappwebview` | 6.1.5 | `openharmony-sig/flutter_inappwebview` | `br_v6.1.5_ohos` | 无（版本一致） |
| `file_picker` | 8.3.7 | `openharmony-sig/fluttertpc_file_picker` | `br_v8.0.7_ohos` | **降 3 个小版本**（OH 侧无 8.3.7 分支） |
| `web`（传递依赖） | 1.1.1 | — | — | 见下方冲突说明 |

**`web` 冲突**：`file_picker 8.0.7` 要求 `web ^0.5.1`，而 `flutter_inappwebview_web` 与上游
`file_picker 8.3.7` 都要求 `web ^1.x`。解法是在覆盖里把 `web` 钉到项目原本已锁定的 `^1.1.0`。
`web` 包只服务 Web 平台，不影响 Android / Windows / 鸿蒙构建。
根治办法是给 fork 提 PR 把 `web: ^0.5.1` 改为 `^1.1.0`（仅一行）。

**无需处理的依赖**：

- `sqflite`（`flutter_cache_manager` 的传递依赖）：无 ohos 实现，但
  `flutter_cache_manager` 在非 Android/iOS/macOS 平台走 `JsonCacheInfoRepository`，
  **鸿蒙运行时不触发 sqflite**。
- `window_manager`：桌面专用，代码里已有 `Platform.isWindows` 守卫，鸿蒙自动空转。
- `flutter_qjs_next`：无 ohos 实现；主线的 `AppCapabilities` 在鸿蒙关闭 `localJsSolver`，
  人机验证自动走纯 Dart ACW 算法（`lib/core/app/acw_pure_dart.dart`），不弹 WebView。
- `gal`：无 ohos 实现；分享图保存自动回退到 `file_picker` 的“另存为”，
  两者都不可用时由能力开关隐藏入口。

## 3. 构建

### 3.1 手工命令（已验证）

> 尝试过把整套流程封装成一键脚本，但此环境下失败点太多（符号链接、提权、hvigor 缓存目录），
> 脚本可靠性达不到日常使用标准，**已放弃脚本方案**，改为下面的手工步骤。
> 踩过的坑见第 5 节，遇到时按那里的说明处理。

```powershell
# 0) 设环境变量（见 1.3）
$flutter = 'C:\Users\admin\fvm\versions\flutter_ohos\oh-3.44.9-dev\bin\flutter.bat'

# 0.5) 生成版本与更新源（发布包必做；本地调试包可跳过）
#      产物 mtbbs_release.json 供 --dart-define-from-file 注入
& .\scripts\version.ps1 ohos -Repo qcxs/mtbbs_app_ohos -Channel release

# 1) 解析依赖（覆盖已写在 pubspec.yaml 的 dependency_overrides 段，无需复制）
#    末尾可能报符号链接错误，无害；若报错就再跑一次
& $flutter pub get

# 2) 出包：模拟器用 x64，真机用 arm64；侧载分发加 --no-codesign
#    正式版（包名 …mtbbs.ohos）带上 mtbbs_release.json（版本号 + 更新源）
& $flutter build hap --release --target-platform ohos-arm64 --no-codesign --dart-define-from-file=mtbbs_release.json
#    调试版（包名 …mtbbs.ohos.debug，可与正式版共存）
& $flutter build hap --debug   --target-platform ohos-x64 --no-codesign --flavor debug
#    beta 版（包名 …mtbbs.ohos.beta；版本文件用 version.ps1 -Beta 生成）
& $flutter build hap --release --target-platform ohos-arm64 --no-codesign --flavor beta --dart-define-from-file=mtbbs_release.json

# 3) 调试运行（可选）
& $flutter devices
& $flutter run -d <device-id>
```

`--target-platform` 可选 `ohos-arm64`（默认）/ `ohos-arm` / `ohos-x64`，**一次只出一个架构**。
步骤 1 与 2 失败时**先原样重跑一次**，多数是环境竞态而非配置错误。

> **不要传 `--target`**：鸿蒙专属的「应用接续」Dart 逻辑已做成 Dart 插件
> `packages/mtbbs_ohos_bridge`（`dartPluginClass` 声明），flutter_tools 构建时自动把它写进
> `.dart_tool/flutter_build/dart_plugin_registrant.dart`，引擎在 isolate 启动时注册。
> 命令行 `build` / `run` 与 DevEco Studio 直接 Run 用的都是默认 `lib/main.dart`，接续能力自动带上。
> `lib/ohos/entry.dart` 仅保留为显式兜底入口（`--target lib/ohos/entry.dart`，安装是幂等的），
> 日常构建**不要**再带它（取舍见 [05-应用流转可行性调研.md](./05-应用流转可行性调研.md) §5.1）。

> 本仓库不需要“用完恢复主线”：它只面向鸿蒙，覆盖文件是仓库的一部分。

### 3.2 「无签名 + 按架构分离」实测数据

| 配置 | 产物 | 体积 | 包内 libs |
|---|---|---|---|
| `debug --flavor debug --target-platform ohos-x64 --no-codesign` | `entry-debug-unsigned.hap` | **165 MB** | 单架构 x64 |
| `release --target-platform ohos-arm64 --no-codesign` | `entry-default-unsigned.hap` | **36.4 MB** | 仅 `libs/arm64-v8a` |
| `release --target-platform ohos-x64 --no-codesign` | `entry-default-unsigned.hap` | **38.9 MB** | 仅 `libs/x86_64` |

要点：

- **体积主要由 `debug`/`release` 决定**（debug 含 VM/JIT 与调试符号），release 比 debug 小约 78%
- **架构必须靠 `--target-platform` 手动分离**，一次构建只产出一个架构的 libs，不存在"一个包含多架构"
- arm64 release 的 libs 构成：`libapp.so` 13.4 MB（AOT Dart）+ `libflutter.so` 16.2 MB（引擎）
  + `libc++_shared.so` 1.2 MB —— 引擎占一半，已无进一步压缩空间
- `--no-codesign` 会提示 `Building for device with codesigning disabled`，属预期；
  产物为 `entry-<flavor>-unsigned.hap`，侧载时由使用者自行签名

### 3.3 应用内更新源（本仓库仓库地址）

上游的「检查更新」改成**构建期注入**（`lib/config/update_config.dart`）：更新源与渠道经
`scripts/version.ps1 -Repo / -Channel` 写进 `mtbbs_release.json`，打包时用
`--dart-define-from-file` 注入。本仓库固定指向自己：

```powershell
& .\scripts\version.ps1 ohos -Repo qcxs/mtbbs_app_ohos -Channel release
```

> 脚本是无 BOM 的 UTF-8：用 PowerShell 7（`pwsh`）或当前 PS7 终端直接执行；
> Windows PowerShell 5.1 会按 ANSI 读中文注释而解析失败，改用 `pwsh -File scripts\version.ps1 ...`。

- **不传 `-Repo`（或未做这一步）的包不检查更新**：关于页不显示更新入口，启动也不发请求，属预期。
- 判新依据是「GitHub Release 创建时间 > 包的构建时间（`mtbbs.time`）」，所以**每次发版都要先跑
  `version.ps1` 再打包**，不要复用旧的 `mtbbs_release.json`。
- Release 需发布在自己的仓库（`qcxs/mtbbs_app_ohos`）并上传 `.hap`；选包只按后缀匹配，
  文件名建议带 ABI（如 `MTBBS_ohos_1.0.0_arm64.hap`）。
- 没有 `.hap` 时用户会看到「打开发布页」，不会出现"无路可走"。
- 关于页展示的仓库地址取注入值，无需改任何文件；`assets/config/sites.json` 的 `app` 快捷链接
  仍是上游地址（该文件随上游镜像，不要手改），需要时可让用户在自己的设置里改。

### 3.4 包名与变体（正式 / beta / debug）

鸿蒙设备上可能通过「卓易通」安装上游 Android APK；包名相同则两者只能二选一。
本仓库把包名统一加 `.ohos` 后缀，并按上游习惯派生 beta / debug 变体：

| 变体 | 包名 | 构建方式 | 产物 |
|---|---|---|---|
| 正式 | `com.github.qcxs.mtbbs.ohos` | 不传 `--flavor`（product `default`） | `entry-default-unsigned.hap` |
| beta | `com.github.qcxs.mtbbs.ohos.beta` | `--flavor beta` | `entry-beta-unsigned.hap` |
| debug | `com.github.qcxs.mtbbs.ohos.debug` | `--debug --flavor debug` | `entry-debug-unsigned.hap` |

- 定义位置：`ohos/build-profile.json5` 的 `products`（包名）+ `ohos/entry/build-profile.json5` 的
  `targets`（hvigor 的输出目录/文件名）。**`--flavor` 与 product/target 同名**，
  漏传 `--flavor` 就是正式版包名（即使加 `--debug`）。
- 三个包名互不相同，可在同一设备同时安装、数据各自独立。
  `flutter run` 默认用正式版包名；要跑 debug 变体用 `flutter run --flavor debug -d <device-id>`；
  DevEco Studio 里在 **Build Variants** 选择对应 product。
- 变体包名不同 → 签名 profile 的 `bundle-name` 必须与目标变体一致
  （侧载分发用的 `--no-codesign` 不受影响）。
- MCP 常驻通知的 Want 不再写死包名，运行时取 `context.applicationInfo.name`
  （`ohos/entry/src/main/ets/plugins/McpStatusNotice.ets`），三个变体都能被通知拉起。
- 校验包名：解包 HAP 读 `pack.info` 的 `summary.app.bundleName`。

## 4. 与上游的边界

本仓库是**独立项目**，只面向鸿蒙构建：

- 依赖覆盖常驻在 `pubspec.yaml` 的 `dependency_overrides` 段；clone 后直接 `flutter pub get`；
- `lib/` 的上游文件与上游保持一致，鸿蒙特有内容放 `ohos/`、`lib/ohos/`、`docs/ohos/`、`dependency_overrides` 段；
- **不要用官方 Flutter 在本仓库构建 Android/Windows**：OH fork 硬编码了
  `TargetPlatform.ohos`，官方 SDK 会直接编译失败：
  `Error: Member not found: 'ohos'.`。需要 Android/Windows 请用主线仓库。
- 上游更新后如何合并见 [03-同步上游.md](./03-同步上游.md)。

业务代码的跨平台差异由主线的 `AppCapabilities`（`docs/23-可选能力与平台降级.md`）处理，
本仓库不需要改 `lib/` 里的业务逻辑。

## 5. 已知坑

1. **`file_picker` 插件符号链接创建失败（高频，最烦人）**——`pub get` / `build hap` 可能报：
   `Cannot create link ... \.plugin_symlinks\file_picker` / `PathNotFoundException (errno 2)`，
   整个 flutter 进程直接崩掉。`file_picker` 从 hosted 依赖变成 git 依赖后必现。
   **处理**：
   - 该错误发生在**依赖已解析、`.flutter-plugins-dependencies` 已写入**之后，因此**无害**；
   - **原样重跑一次基本就过**（实测 release 首次失败、重跑成功；Android 侧一次就过）；
   - 不要试图"预建好链接让它跳过"：`New-Item -ItemType SymbolicLink` 在 PS 5.1 里
     **需要管理员权限**（不带免提权标志），未提权一定失败；而 Dart 侧创建又报 errno 2。
     实测这条路走不通，别浪费时间。
   - 想彻底避免：用管理员权限/开启开发者模式的终端执行，或改用 `git worktree` 让鸿蒙独占一个目录。
     实测**开发者模式已开启**（`AllowDevelopmentWithoutDevLicense=1`）也仍然复现，故首选"重试"。
2. **`undefined (reading 'filter')` 报错（DevEco 里点构建必踩）**——症状：

   ```
   > hvigor ERROR: 00305010 Syntax Error
   Error Message: TypeError Cannot read properties of undefined (reading 'filter')
   0 task in total: 0 executed, 0 up-to-date.
   ```

   报错让你去查 `hvigorconfig.ts` / `hvigorfile.ts`，**跟那两个文件毫无关系**。
   真实根因：`ohos/node_modules/flutter-hvigor-plugin` 读 `.flutter-plugins-dependencies`
   的 `plugins.ohos` 后直接 `.filter(...)`，而该文件**没有 `ohos` 段**。

   什么时候会没有：`.flutter-plugins-dependencies` 由 flutter 工具生成，
   **官方 SDK** 生成的清单不含 `ohos`（主线态），**Flutter-OH SDK** 生成的才含。
   本仓库的依赖覆盖常驻在 `pubspec.yaml`，正常 `pub get` 生成的清单就应有 `ohos` 段；
   若 DevEco 里仍报此错，先重跑一次 `pub get` 再自检——

   ```powershell
   & $flutter pub get        # $flutter 为 Flutter-OH SDK 的 flutter
   (Get-Content .flutter-plugins-dependencies -Raw | ConvertFrom-Json).plugins.ohos.name
   # 应输出 file_picker / flutter_inappwebview_ohos / path_provider_ohos / url_launcher_ohos
   ```

   **建议**：鸿蒙出包走 `flutter build hap`（它自己会保证清单正确），
   DevEco 只用来配签名/安装，避免在两种状态间反复切换。
3. **沙箱/权限**——hvigor 要写 `~/.hvigor/project_caches`，在受限环境会报
   `EPERM: operation not permitted, mkdir 'C:\Users\admin\.hvigor\...'`。
   构建需在普通（非受限）终端执行。
4. **`flutter create` 的副作用**——会生成 `test/widget_test.dart`（模板用例，引用不存在的
   `MyApp`）并改动 `.metadata`，需按需清理。
5. **`file_picker` 版本缺口**——OH 侧只有 8.0.7 / 10.2.0 / 10.3.8 分支。当前选 8.0.7
   （同大版本、API 兼容，`flutter analyze lib` 通过）。若将来要用 10.x，需同步改业务代码。
6. **`flutter_inappwebview` 的 keep-alive 缺陷**——OH fork 未正确实现
   `InAppWebViewKeepAlive`：页面从路由栈弹出后原生 WebView 被销毁，再次进入会重新加载。
   Android/iOS 正常。属社区 fork 缺陷，只能等上游修。
7. **`version.ps1` 可复用**——版本号脚本与 `mtbbs_release.json` 与平台无关，HAP 构建可直接沿用；
