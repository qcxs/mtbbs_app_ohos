# 应用流转（应用接续）可行性调研

> 适用：评估"鸿蒙应用接续/流转"要不要做、怎么做、代码放哪。结论已落地实现，实施记录见 §11。
> 结论先行：**技术上可行，但不是"无缝迁移"而是"重建 + 恢复导航状态"**；代码可以 100% 落在下游
> （`ohos/` + `lib/ohos/`），不需要改上游。

## 0. 结论摘要

| 项 | 结论 |
|---|---|
| 可行性 | **可行**（官方能力成熟，API 12+ 免权限） |
| 可达到的效果 | 对端设备上**重新打开 App 并落到同一页面/同一帖子**；不是像素级无缝（Flutter UI 状态无法跨设备搬运） |
| 前置条件 | **两台真机**（HarmonyOS 5.0.5+，模拟器不支持）、双端装同一应用、系统设置开启"多设备协同 > 接续" |
| 主要风险 | 目标端走的是 `onWindowStageRestore`，而 Flutter-OH 的 `FlutterAbility` **没有实现它** → 不处理会对端**白屏**（见 §4.1） |
| 代码落点 | 原生全部在 `ohos/`；Dart 全部在 `lib/ohos/`（下游专属目录）；**上游改动 0** |
| 合并影响 | `lib/ohos/` 上游永不存在 → 每次合并零冲突；上游 `lib/` 大重构也不影响该目录（见 §5） |
| 参考实现 | `PiliPlus-ohos`（同为 Flutter 鸿蒙版）**已真机跑通**视频/直播/音频/专栏四类接续，本文的回调时序、通道契约、可用态控制均按它的做法校正（见 §4.4、§4.5、§5.2） |
| 估算 | P0（路由级接续 + 可接续态）≈ 2 个原生文件、2 个 Dart 文件；P1（编辑草稿接续）复用现有快照机制 |

## 1. 官方能力是什么

"应用流转"在 HarmonyOS 上的落地形态是**应用接续（Continuity）**：源端前台运行 App，用户在对端
Dock 栏点该应用的接续图标，系统把页面栈与业务数据送到对端，对端在相同应用中接着用。

| 环节 | 回调 | 说明 |
|---|---|---|
| 源端保存 | `UIAbility.onContinue(wantParam): OnContinueResult \| Promise<...>` | 返回 `AGREE` / `REJECT` / `MISMATCH`；数据写进 `wantParam` |
| 目标端（冷启动/多实例热启动） | `onCreate(want, launchParam)`，`launchParam.launchReason === LaunchReason.CONTINUATION` | 读 `want.parameters` 恢复 |
| 目标端（单实例热启动） | `onNewWant(want, launchParams)` | 同上 |
| 目标端页面栈恢复 | `onWindowStageRestore(windowStage)` | **冷启动**时系统调用它而不是 `onWindowStageCreate`；热启动（`singleton` 已在前台）走 `onNewWant`，窗口无需恢复 |
| 可用态控制（强烈建议） | `context.setMissionContinueState(ACTIVE / INACTIVE)` | 默认 `INACTIVE` = 对端不显示接续入口；有可接续内容时再置 `ACTIVE`，避免"点了却失败" |

工程配置（`ohos/entry/src/main/module.json5`）：

- `abilities[].continuable: true`（默认 `false` = 系统认定为不可迁移）；
- `launchType` 用 `singleton`（本仓库未显式配置，stage 模型默认即 `singleton`，**无需改**）。

数据通道二选一：

- `wantParam`：**< 100 KB**，够放"路由 + tid + 少量参数"；
- 分布式数据对象（`@ohos.data.distributedDataObject`）：500 KB 上限，同 `bundleName` 同 `sessionId`。
  本项目 P0 用不到。

## 2. 使用限制（全部为硬限制）

- **模拟器不支持**，必须两台真机；HarmonyOS 5.0.5 Release 及以上；
- 双端都要装该应用，且 `bundleName` 相同（本仓库 `com.github.qcxs.mtbbs`）；
- 双端需在"设置 > 多设备协同 > 接续"中开启；
- **API 12 起无需 `ohos.permission.DISTRIBUTED_DATASYNC`**（本项目 compatibleSdkVersion 17，免权限）；
- `onContinue` 里 `wantParam` 要避开系统预置 key（`version`、`targetDevice` 等）。

## 3. 这个项目能接续到什么程度

Flutter 的 UI 状态（Widget 树、滚动位置、输入框内容）**无法跨设备搬运**：目标端是新的
`UIAbility` 实例 → 新 Flutter 引擎 → Dart 重新 `main()`。所以只能"重建 + 按快照恢复"。

| 级别 | 恢复内容 | 手段 | 成本 |
|---|---|---|---|
| **P0（建议先做）** | 当前页面：帖子详情 `tid`、版块 `fid`、搜索词、用户主页 uid | 路由 location + `GoRouter.go()` | 小 |
| P1 | 编辑器草稿（标题/正文） | 复用现有编辑器快照（`EditorHistoryProvider`） | 中 |
| P2 | 具体滚动位置 / 阅读进度 | 需要页面级上报 + 首帧后定位，易抖动 | 大，不建议 |
| 不做 | 像素级无缝、播放进度 | Flutter 侧不可行 | — |

## 4. Flutter 侧的五个硬约束

### 4.1 目标端必须自己接 `onWindowStageRestore`（否则白屏）

`FlutterAbility` 只实现了 `onWindowStageCreate`（建 delegate、建 FlutterView、`loadContent`）。
接续冷启动时系统调用的是 `onWindowStageRestore`，基类没有实现 → **Flutter 界面不会被创建（对端白屏）**。
PiliPlus-ohos 的实测做法是**两处都要补**：

```ets
onCreate(want: Want, launchParam: AbilityConstant.LaunchParam) {
  // Want 暂存类（MCP 通知点击）放在 super 之前
  McpStatusNotice.handleWant(want)
  super.onCreate(want, launchParam)
  // 接续判定与窗口恢复必须放在 super.onCreate 之后（基类要先建好引擎/delegate）
  if (this.handleContinuation(want, launchParam, false)) {
    this.context.restoreWindowStage(new LocalStorage())
  }
}

// 基类没实现：接续冷启动时系统调它，而不是 onWindowStageCreate
onWindowStageRestore(windowStage: window.WindowStage): void {
  this.onWindowStageCreate(windowStage)
}
```

这是本功能最大的坑，放在第一步验证（见 §6 第 1 步、§7 第 4 条）。

### 4.2 源端数据要从 Dart 拉 → 通道 + 超时兜底

`onContinue` 在 Ability 层执行，拿不到 Dart 的当前路由。PiliPlus 的做法是**反向拉取**：
`onContinue` 里通过 MethodChannel 向 Dart 要快照（`getContinuationState`），**1.5 s 超时**
（`onContinue` 受系统时限约束，超时就返回 `REJECT`，绝不能让接续流程卡死）。

比"Dart 主动 push 缓存"更好：不会拿到过期快照，也不需要每次路由变化都同步一次。
`onContinue` 的签名带 Promise 返回值：

```ets
async onContinue(wantParam: Record<string, Object>): Promise<AbilityConstant.OnContinueResult> {
  const state = await this.bridge.getContinuationState();   // 内部 1.5 s 超时
  if (state == null) return AbilityConstant.OnContinueResult.REJECT;
  wantParam['mtbbs_continuation'] = state;
  return AbilityConstant.OnContinueResult.AGREE;
}
```

### 4.3 目标端恢复要等 Dart 首帧

`onWindowStageRestore`/`onCreate` 早于 Dart 首帧，此时根 Navigator 未挂载，直接 `go()` 会静默失败。
沿用现有"暂存 + 首帧补取"模式：ArkTS 存 `pendingContinuation` → Dart 首帧后
`getPendingContinuation` 取走再 `router.go()`（与 `McpStatusNotice` 的 `getPendingTap` 同构）。

两个必须守住的条件（PiliPlus 都踩过）：

- **冷启动不要推送**：`setPendingContinuation(data, notify: false)`。冷启动时 Dart handler 还没注册，
  原生 `invokeMethod` 会进引擎的 channel buffer，在 Dart 注册 handler 的瞬间（首帧前后、根路由
  尚未挂载）**回放**，数据被提前取走 → 无处跳转、直接丢失；冷启动统一由 Dart 首帧后主动拉取。
- **路由未就绪不要消费**：`getPendingContinuation` 取走即清空，Dart 必须先判"根路由可用"再取
  （PiliPlus 用 `Get.key.currentState == null` 提前 return；GoRouter 用
  `rootNavigatorKey.currentContext == null` 提前 return，并在首帧回调里重试）。

### 4.4 接续可用态：默认关闭，按页面持有动态激活

系统对"能不能接续"还有一层运行时开关：`context.setMissionContinueState(ACTIVE | INACTIVE)`。
PiliPlus 的做法值得照抄：

- `onCreate` 里默认置 `INACTIVE`——没有可接续内容时，对端**不显示接续入口**，避免用户点了却失败；
- Dart 侧"可接续态"：PiliPlus 是在每个可接续页面里 `hold(owner)` / `release(owner)`。它建立在
  `lib/harmony_adapt/` + 页面侵入调用上，**我们改不了上游页面**，所以换成零侵入版本：
  监听 `GoRouter`（`routerDelegate.addListener`），按当前 `location` 是否命中可接续路由模式
  （`/thread/:tid`、`/forum/:fid` 等）切换 `ACTIVE / INACTIVE`；`onContinue` 时同样按当前
  `location` 生成快照——快照本来就是"用时拉取"，天然是最新值，不需要持有者栈。
- `onContinue` 拿不到快照（不在可接续页面）时返回 `REJECT`。

> 这个替换让接续保持**上游 0 改动**：页面里不需要任何 hold/release 调用，路由监听只在
> `lib/ohos/` 里装一次。这也是 03 第 13 节点出的结论——PiliPlus 能侵入是因为它是上游分支，
> 我们不能照抄侵入点。

这同时解决了 §9 的第 4 个决策项：不需要额外的用户设置开关，系统侧状态就是准确的。

### 4.5 通道契约（对齐 PiliPlus）

单条 `MethodChannel`，在 `configureFlutterEngine` 里注册（与 `McpStatusNotice` 同一时机）：

| 方向 | 方法 | 说明 |
|---|---|---|
| ArkTS → Dart（请求/应答） | `getContinuationState` | 源端 `onContinue` 拉当前快照（JSON 字符串或 null），原生侧 1.5 s 超时 → null |
| ArkTS → Dart（推送） | `onContinuationRestore` | 对端**热启动**（`onNewWant`）时推送，Dart 立即去取 |
| Dart → ArkTS | `getPendingContinuation` | 取走暂存数据（取走即清空）；冷启动首帧、路由就绪后调用 |
| Dart → ArkTS | `setContinuationActive` | `{active: bool}` → `setMissionContinueState` |

原生侧只需一个 `pendingContinuation: string | null` 内存字段，不做持久化。

## 5. 代码落点与合并策略

| 内容 | 位置 | 归属 |
|---|---|---|
| `module.json5` 的 `continuable: true`、`onContinue` / `onWindowStageRestore` / `onCreate` 恢复 | `ohos/entry/src/main/ets/...` | 下游 |
| 通道实现（`mtbbs/continuation`：`getContinuationState` / `getPendingContinuation` / `onContinuationRestore` / `setContinuationActive`） | `ohos/.../plugins/ContinuationBridge.ets`（沿用 `McpStatusNotice.ets` 的注册方式） | 下游 |
| Dart 侧：持有者栈、快照生成、首帧补取、`router.go()` | **`lib/ohos/continuation.dart`** + `lib/ohos/continuation_bridge.dart` | 下游 |
| 启动入口（把 `lib/ohos` 挂进 App） | `lib/ohos/entry.dart` + 构建时 `--target` | 下游 |

**上游改动 0**，理由见 [03-同步上游.md](./03-同步上游.md) 的 `lib/ohos/` 规则：
上游不存在该目录，`git merge` 不会产生冲突；上游 `lib/` 大重构（拆文件/改名）也不影响它，
因为下游只在 `lib/ohos/` 里 `import 'package:mtbbs/...'`，重构后编译期就会报错、可被
`flutter analyze` 立刻发现，而**不会**制造 merge 冲突。

### 5.1 入口方案对比（关键决策）

| 方案 | 做法 | 上游改动 | 缺点 |
|---|---|---|---|
| **A（推荐）** | 自定义入口 `lib/ohos/entry.dart`，构建/运行带 `--target lib/ohos/entry.dart` | 0 | 所有 `build hap` / `run` 命令都要带 `--target`（写进 `docs/ohos/01`） |
| B | 上游 `lib/main.dart` 加 1 行 hook 调用 | 1 行 × 永久 | 上游大重构后这 1 行要重打；下游文件会出现在 `lib/` 差异里 |
| C | 每次合并后 AI 重新打补丁 | 0 | 依赖 AI 记忆，最易漏 |

PiliPlus-ohos 直接把接续写进 `lib/harmony_adapt/` 并改了 `lib/main.dart`（一处首帧回调）——
因为它是上游的 fork，动 `lib/` 无所谓。本仓库不 fork 上游（规则见 [03](./03-同步上游.md)），所以取 A。

A 的入口文件内容（约 6 行）：

```dart
import 'package:flutter/widgets.dart';
import 'package:mtbbs/main.dart' as app;
import 'package:mtbbs/ohos/ohos_bootstrap.dart';

void main() {
  WidgetsFlutterBinding.ensureInitialized();
  OhosBootstrap.install();   // 挂通道 + 首帧补取 pending
  app.main();
}
```

> `ensureInitialized()` 必须先调：`MethodChannel.setMethodCallHandler` 需要 Binding。
> `lib/main.dart` 自己也会调，重复调用是幂等的。

### 5.2 参考实现骨架（PiliPlus-ohos，可照抄结构）

原生 `ohos/entry/src/main/ets/plugins/ContinuationBridge.ets`：

```ets
export class ContinuationBridge {
  private static channel: MethodChannel | null = null
  private static pending: string | null = null

  static register(engine: FlutterEngine) { ... }        // configureFlutterEngine 里调

  /** 源端 onContinue 时调用：向 Dart 拉快照，1.5 s 超时兜底（success/error/notImplemented 都 resolve） */
  static getState(): Promise<string | null> { ... }

  /** 对端收到接续数据：冷启动 notify=false（只暂存），热启动 notify=true（推送让 Dart 立即取） */
  static setPending(data: string, notify: boolean) {
    ContinuationBridge.pending = data
    if (notify) ContinuationBridge.channel?.invokeMethod('onContinuationRestore', null)
  }
  // Dart 侧方法：getPendingContinuation（取走即清空）/ setContinuationActive（setMissionContinueState）
}
```

Dart `lib/ohos/continuation.dart`：

```dart
abstract class Continuation {
  static final List<Object> _owners = [];

  /// 页面进入/退出时调用；栈空→非空 激活，释放到空 关闭
  static void hold(Object owner) { ... }
  static void release(Object owner) { ... }

  /// 源端：从最近的持有者生成快照 JSON；无可接续内容返回 null
  static String? currentState() { ... }

  /// 对端：路由就绪后取走 pending 并 go()
  static Future<void> restorePending() async {
    if (rootNavigatorKey.currentContext == null) return;   // 未就绪，交给首帧后的重试
    final data = await _channel.invokeMethod<String>('getPendingContinuation');
    if (data == null) return;
    final map = jsonDecode(data) as Map<String, dynamic>;
    switch (map['type']) {
      case 'thread': router.go('/thread?tid=${map['tid']}&page=${map['page']}');
      case 'forum': router.go('/forum?fid=${map['fid']}');
    }
  }
}
```

> 具体路由与快照字段按本仓库 `lib/config/router.dart` 的实际路径调整；`page` 之类可选。
> PiliPlus 的 `hold/release` 是我们不采用的侵入写法——本仓库改为监听 GoRouter 的 `location`（§4.4）。

## 8. 风险与待确认

| 风险 | 影响 | 缓解 |
|---|---|---|
| Flutter-OH 未实现 `onWindowStageRestore` | 对端白屏 | PiliPlus-ohos 已用「转发到 `onWindowStageCreate` + `onCreate` 里 `restoreWindowStage`」真机跑通，风险已降级；仍按 §6 第 1 步先验证 |
| 自定义 `--target` 是否被 `build hap` 完整支持 | 构建可能忽略入口 | 先跑一次空壳入口验证；不行则退回方案 B（上游 1 行 hook） |
| 引擎冷启动耗时导致"接续后要等首屏" | 体验 | 数据小，可先展示 loading；PiliPlus 同样如此 |
| `wantParam` 100 KB | 只影响大对象 | P0 只放路由/短参数 JSON |
| `onContinue` 有系统时限 | 接续卡死或失败 | 向 Dart 拉快照加 1.5 s 超时，超时 `REJECT`（PiliPlus 实测值） |
| 冷启动接续数据被提前回放消费 | 数据丢失、对端停在首页 | 冷启动 `notify=false` + Dart 判路由就绪再取（§4.3） |

## 9. 决策项（请选）

1. **做 / 不做**：是否值得为鸿蒙单独引入这套原生能力（上游完全不需要）。
2. **范围**：只做 P0（路由级），还是连 P1（编辑草稿）一起。
3. **入口方案**：A（自定义 `--target`，上游 0 改动）还是 B（上游 1 行 hook）。
4. **可接续态**：照 PiliPlus 做法（默认 `INACTIVE` + 页面持有自动激活、无设置开关），还是再加一个用户级开关？

### 11.2 与 §5.2 骨架的差异（有意为之）

1. **快照格式改为 `{"location": "<app 路由 location>"}`**：不再按 `type/tid/page` 逐字段拆解。
   `GoRouter` 的 location 本身就是可直接重放的完整状态（含 `page` / `pid` / `authorid` 等查询参数），
   对端 `router.go(location)` 即可原样落回；新增可接续页面只需改 `_isContinuable()` 的判断。
2. **可接续路由白名单**：`/thread/:tid`（排除 `/thread/cache` 本地只读缓存页）与 `/forum?fid=`。
   其余页面（首页、搜索、用户等）不可接续——快照为 null 时 `onContinue` 返回 `REJECT`。
3. **不再使用页面 `hold/release`**：`Continuation` 只监听 `GoRouter` 的 `routerDelegate`，
   上游页面零改动；`_syncActive()` 在 location 变化时切换 `ACTIVE / INACTIVE`。
4. **GoRouter 获取方式**：`rootNavigatorKey.currentContext` 非空后 `GoRouter.maybeOf(context)`
   （`go_router` 把根 Navigator 包在 `InheritedGoRouter` 里，可从此获取）。
   首帧未就绪时逐帧重试 3 次，之后由 `getContinuationState` / `onContinuationRestore` 的按需绑定兜底。
