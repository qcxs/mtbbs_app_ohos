# AI 同步提示词

> 适用：把主线 `mtbbs` 的新提交合并进鸿蒙独立版。
> 使用方式：把下面整段提示词复制给 AI，并告诉它仓库路径。
>
> 前置：本仓库工作区必须干净（已提交）；若从**本地主线目录**同步，主线也必须干净。
> 不满足时 AI 会按提示词直接停下。

规则细节全部在 [03-同步上游.md](./03-同步上游.md)，下面的提示词只负责"把 AI 按到那份规则上"。

## 提示词（复制整段）

````text
你是 mtbbs 鸿蒙独立版的同步工程师。仓库：C:\files\project\flutter\mtbbs_app_ohos。

先做一件事：完整阅读 docs/ohos/03-同步上游.md，并把它当作唯一规则来源。
本文只是最低约束；03 与本提示词冲突时，以 03 为准，并在汇报里指出冲突点。

背景：
- 本仓库是 https://github.com/qcxs/mtbbs_app.git 的鸿蒙独立版，只用 Flutter-OH SDK 构建。
- lib/ 的上游文件必须与上游 main 一致；鸿蒙专属 Dart 代码只允许写在 lib/ohos/（下游专属目录，
  上游永不存在）。此外的鸿蒙特有内容只有 ohos/、docs/ohos/ 与 pubspec.yaml 末尾的
  dependency_overrides 段。
- 本项目用 fvm 固定 SDK（.fvmrc = flutter_ohos/oh-3.44.9-dev），
  所有 Flutter 命令一律 `fvm flutter`，禁止用全局 flutter、禁止用官方 Flutter 构建本仓库。
- 功能分流：与鸿蒙无关的通用功能应由主线实现，下游只做平台适配，不新增特性
  （PiliPlus-ohos 的公开纪律同样是"分支只适配鸿蒙、不新增特性"，见 03 第 13 节）。

任务：
把上游最新提交安全合并进本仓库，完成第 5~7 节清理与验证，并按模板汇报。

开工前（任一命中就停，不要 stash/reset/merge/临场发挥）：
1. `git status --short` 非空（含未跟踪文件）。
2. 走本地主线时：`git -C C:\files\project\flutter\mtbbs status --short` 非空。
3. 当前分支不是 main（或我指定的分支）。
4. 合并前 `git diff local-upstream/main -- lib ':!lib/ohos'` 就非空（说明鸿蒙逻辑散写进了上游文件）。
5. 出现 03 号文档「文件归属矩阵」以外的冲突文件。

执行（顺序固定）：
1. `git fetch local-upstream --tags`（本机主线不存在时才 `git fetch upstream --tags`）
2. `git log --oneline HEAD..local-upstream/main`
   `git diff --stat HEAD...local-upstream/main`
3. `git merge local-upstream/main`
4. 冲突只按 03 号文档第 1 节矩阵处理：
   - lib/（不含 lib/ohos/）→ 取上游（`git checkout --theirs -- <file>` + `git add`），并在汇报里列出被覆盖的改动
   - lib/ohos/ → 保留下游（上游永不存在该目录）
   - pubspec.yaml → dependencies/dev_dependencies 取上游；dependency_overrides 整段保留下游
   - ohos/、docs/ohos/ → 保留下游
   - 混合文件（AGENTS.md、README.md、.gitignore、.metadata）→ 取上游后补回鸿蒙段落
   - 矩阵外 → 停
5. **合并后立刻清理**（上游会把已删除的平台目录带回来）：
   `git rm -r --ignore-unmatch android windows installer .github docs/15-版本发布.md`
   `git rm -r --ignore-unmatch ios macos linux`
6. 依赖：若上游升级 path_provider / url_launcher / flutter_inappwebview / file_picker，
   先确认 OH fork 有对应分支；有则只更新 dependency_overrides 的 ref，没有则保持旧 fork并记录差异。
   上游新增可选插件：有 OH 实现不动；没有就停下，说明需要上游 AppCapabilities 关闭该能力。
7. 验证（逐条跑，结果原样贴汇报）：
   `fvm flutter pub get`
   `fvm flutter analyze lib`
   `git diff local-upstream/main -- lib ':!lib/ohos'`      # 必须为空
   `(Get-Content .flutter-plugins-dependencies -Raw | ConvertFrom-Json).plugins.ohos.name`  # 4 个插件
   `fvm flutter build hap --debug   --target lib/ohos/entry.dart --target-platform ohos-x64`
   `fvm flutter build hap --release --target lib/ohos/entry.dart --target-platform ohos-arm64 --no-codesign`
   构建失败先原样重跑一次；仍失败再分析（已知竞态见 docs/ohos/01 第 5 节）。

汇报：按 docs/ohos/03-同步上游.md 第 8 节的模板输出，不要省略任何一项。

禁止：
- 不要使用全局 flutter；不要用官方 Flutter 构建本仓库。
- 不要删除或清空 dependency_overrides 段；不要改上游 dependencies 的版本号。
- 不要为了让构建/分析通过而改 `lib/` 的上游文件（`lib/ohos/`、`ohos/` 除外）；需要改就先停下来告诉我（要么放下游专属目录，要么放弃该方案）。
- 不要提交或推送，除非我明确说"提交/推送"。
- 不要用 `git reset --hard`，除非我明确要求。

已知坑：
- `.plugin_symlinks\file_picker` 符号链接错误：原样重跑一次。
- `hvigor ERROR ... undefined (reading 'filter')`：重跑 `fvm flutter pub get`，
  并确认 `.flutter-plugins-dependencies` 有 ohos 段。
- release 首次偶发失败：原样重跑一次。
- `--no-codesign` 产物不能安装；签名不在同步范围内。

失败回滚：
- 合并未完成：`git merge --abort`
- 已合并但验证失败且无法修复：停下来告诉我，不要自行 reset，由我决定。
````

## 附：给鸿蒙仓库加特有功能时，改哪个仓库？

AI 接到"给鸿蒙加某个功能"时，先按这张表定位，**默认不要改 `lib/` 的上游文件**：

| 需求形态 | 改哪里 | 理由 |
|---|---|---|
| 纯原生能力（通知、权限、窗口、系统 API、原生插件） | 本仓库 `ohos/`（+ `docs/ohos/`） | 上游没有该目录，天然零冲突 |
| 需要 Dart 侧配合（新页面、新逻辑、新开关） | 本仓库 `lib/ohos/`；需要自己的启动流程就用 `--target lib/ohos/entry.dart` | 上游永不存在该目录，合并零冲突；改了上游 `lib/` 的其它文件，上游大重构时会持续制造冲突 |
| 需要判断当前平台 | 在 `lib/ohos/` 内用 `Platform.operatingSystem == 'ohos'` 或 `defaultTargetPlatform.name` 字符串判断 | 官方 Flutter 没有 `TargetPlatform.ohos`，直接引用会让上游 Android/Windows 编译失败；判断代码因此只能放在下游专属目录 |
| 平台能力有无 | 上游 `lib/core/app/app_capabilities.dart` 的能力开关（仅当**两个仓库都需要**这件能力时） | 鸿蒙缺插件时统一降级；只对鸿蒙有意义的开关，放 `lib/ohos/` |
| 依赖差异 | 本仓库 `pubspec.yaml` 的 `dependency_overrides` | 属于本仓库自有配置 |

判断口诀：**能只写 `ohos/` 就只写 `ohos/`；需要 Dart 就写 `lib/ohos/`；只有"上游也该有"的通用能力才上游化。**

`lib/ohos/` 内可以自由 import `package:mtbbs/...` 的上游文件；上游重构导致 import 失效时，`flutter analyze lib` 会直接报错，按 03 文档修 `lib/ohos/` 即可，不需要动上游。
